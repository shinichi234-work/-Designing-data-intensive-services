## Часть 1. Теоретическое введение: технологии, используемые в работе (15 минут)

### 1.1. Reverse proxy: что это и зачем

**Reverse proxy** (обратный прокси) — это сервер, который стоит перед вашими backend-сервисами и принимает все запросы от клиентов, перенаправляя их на внутренние сервисы. Клиент думает, что общается напрямую с сервером, но на самом деле все запросы проходят через прокси.

**Аналогия:** Представьте ресепшн в большом офисе. Посетитель приходит на ресепшн, а администратор направляет его к нужному сотруднику. Посетитель не знает, где именно сидит сотрудник и сколько их — он просто оставляет запрос на ресепшене и получает ответ.

**Зачем нужен reverse proxy в высоконагруженных системах:**

| Задача | Как решает Nginx |
|---|---|
| **Балансировка нагрузки** | Распределяет запросы между несколькими экземплярами сервиса |
| **Отказоустойчивость** | Если один экземпляр упал — трафик идёт на остальные |
| **Терминация SSL** | Расшифровка HTTPS происходит на прокси, backend работает по HTTP |
| **Кеширование** | Nginx может кешировать статические файлы и ответы API |
| **Сжатие** | Gzip/Brotli сжатие ответов для уменьшения трафика |
| **Rate limiting** | Ограничение количества запросов от одного клиента |
| **Скрытие внутренней структуры** | Клиент не знает, сколько у вас серверов и какие у них адреса |

**Nginx** — самый популярный reverse proxy в мире. Он используется в продакшене большинства крупных компаний: Netflix, Dropbox, WordPress, GitHub.

### 1.2. Балансировка нагрузки: алгоритмы

**Балансировка нагрузки** — это распределение входящих запросов между несколькими backend-серверами для оптимизации использования ресурсов и повышения отказоустойчивости.

**Основные алгоритмы Nginx:**

| Алгоритм | Директива | Как работает | Когда использовать |
|---|---|---|---|
| **Round Robin** (по умолчанию) | — | Запросы распределяются по серверам по очереди | Серверы одинаковой мощности, короткие запросы |
| **Least Connections** | `least_conn` | Запрос идёт на сервер с наименьшим числом активных соединений | Длинные запросы, разная нагрузка |
| **IP Hash** | `ip_hash` | Один клиент всегда попадает на один и тот же сервер | Сессии, требующие привязки к серверу |
| **Weighted** | `weight=N` | Сервер с большим весом получает больше запросов | Серверы разной мощности |

**Round Robin** — самый простой алгоритм: запрос 1 → сервер A, запрос 2 → сервер B, запрос 3 → сервер C, запрос 4 → сервер A, и так далее.

**Least Connections** — более умный алгоритм: Nginx сравнивает текущее количество активных соединений на каждом сервере и отправляет новый запрос на тот, где их меньше всего. Это лучше подходит для сценариев, где время обработки запросов варьируется.

**Для нашей работы** мы будем использовать Round Robin как базовый алгоритм, а затем поэкспериментируем с Least Connections.

### 1.3. Health checks: как Nginx узнаёт, что сервер упал

Nginx поддерживает **пассивные health checks** через директивы `max_fails` и `fail_timeout`:

```nginx
upstream backend {
    server fastapi-app1:8000 max_fails=3 fail_timeout=30s;
    server fastapi-app2:8000 max_fails=3 fail_timeout=30s;
    server fastapi-app3:8000 max_fails=3 fail_timeout=30s;
}
```

- **`max_fails=3`** — если сервер не ответил 3 раза подряд, Nginx помечает его как «недоступный»
- **`fail_timeout=30s`** — на 30 секунд сервер исключается из балансировки; через 30 секунд Nginx попробует снова

Это означает: если один из экземпляров FastAPI упал, Nginx перестанет отправлять на него запросы в течение 30 секунд, а трафик пойдёт на оставшиеся серверы.

### 1.4. Docker Compose: оркестрация нескольких контейнеров

**Docker Compose** — инструмент для определения и запуска многоконтейнерных Docker-приложений. С его помощью мы опишем в одном файле `docker-compose.yml` три экземпляра FastAPI и один Nginx, а затем запустим их одной командой.

**Ключевые концепции Docker Compose:**

| Концепция | Описание |
|---|---|
| **Service** | Описание контейнера: образ, порты, переменные окружения, зависимости |
| **Network** | Виртуальная сеть, в которой контейнеры видят друг друга по именам |
| **Volume** | Монтирование файлов с хоста в контейнер (для конфигураций) |
| **depends_on** | Зависимости между сервисами (Nginx ждёт запуска FastAPI) |

### Шаг 2. Создание Dockerfile (10 минут)

Создайте файл `Dockerfile` в директории `practice-2`:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

# Копируем и устанавливаем зависимости отдельно (кеширование слоёв)
COPY app/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Копируем код приложения
COPY app/main.py .

# Открываем порт (документация)
EXPOSE 8000

# Запускаем Uvicorn
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Разбор Dockerfile:**

- `FROM python:3.12-slim` — базовый образ: Python 3.12 в минимальном варианте (slim). Полный образ `python:3.12` весит ~1 ГБ, `slim` — ~150 МБ.
- `WORKDIR /app` — рабочая директория внутри контейнера. Все последующие команды выполняются относительно неё.
- `COPY app/requirements.txt .` — копируем только файл зависимостей. Это делается **до** копирования кода, чтобы Docker мог закешировать слой с установкой зависимостей. Если код изменится, а `requirements.txt` — нет, Docker не будет переустанавливать зависимости.
- `RUN pip install --no-cache-dir -r requirements.txt` — устанавливаем зависимости. Флаг `--no-cache-dir` отключает кеш pip, уменьшая размер образа.
- `COPY app/main.py .` — копируем код приложения.
- `CMD ["uvicorn", ...]` — команда, которая выполняется при запуске контейнера.

### Шаг 3. Создание конфигурации Nginx (15 минут)

Создайте файл `nginx.conf` в директории `practice-2`:

```nginx
worker_processes auto;

events {
    worker_connections 1024;
}

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    # Формат логов с upstream-сервером
    log_format upstream_log '$remote_addr - $upstream_addr - '
                           '"$request" $status $body_bytes_sent '
                           '"$http_referer" "$http_user_agent"';

    access_log /var/log/nginx/access.log upstream_log;

    # Группа upstream-серверов
    upstream fastapi_backend {
        least_conn;  # Алгоритм балансировки: least connections

        server app1:8000 max_fails=3 fail_timeout=30s;
        server app2:8000 max_fails=3 fail_timeout=30s;
        server app3:8000 max_fails=3 fail_timeout=30s;

        keepalive 32;  # Keep-alive соединения к backend
    }

    server {
        listen 80;
        server_name localhost;

        # Основной проксирующий location
        location / {
            proxy_pass http://fastapi_backend;

            # Стандартные заголовки для проксирования
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            # Таймауты
            proxy_connect_timeout 5s;
            proxy_send_timeout 30s;
            proxy_read_timeout 30s;

            # Retry при ошибках
            proxy_next_upstream error timeout http_500 http_502 http_503 http_504;
            proxy_next_upstream_tries 2;
        }

        # Health-check эндпоинт Nginx
        location /nginx-health {
            return 200 "OK\n";
            add_header Content-Type text/plain;
        }
    }
}
```

**Разбор конфигурации:**

**Блок `upstream fastapi_backend`** — это группа backend-серверов. Имена `app1`, `app2`, `app3` — это имена сервисов в Docker Compose, которые разрешаются в IP-адреса контейнеров через встроенный DNS Docker.

**`least_conn`** — алгоритм балансировки: запрос идёт на сервер с наименьшим числом активных соединений.

**`max_fails=3 fail_timeout=30s`** — пассивный health check: после 3 неудачных попыток сервер исключается из балансировки на 30 секунд.

**`keepalive 32`** — Nginx будет поддерживать до 32 idle keep-alive соединений к каждому backend-серверу. Без этой директивы каждый запрос создавал бы новое TCP-соединение (полный handshake), что добавляет задержку.

**`proxy_next_upstream`** — если backend вернул ошибку (500, 502, 503, 504) или таймаут, Nginx попробует следующий сервер из группы.

**`log_format upstream_log`** — кастомный формат логов, который записывает `$upstream_addr` — адрес backend-сервера, обработавшего запрос. Это позволит нам увидеть, как распределяются запросы.

### Шаг 4. Создание docker-compose.yml (10 минут)

Создайте файл `docker-compose.yml` в директории `practice-2`:

```yaml
services:
  app1:
    build: .
    container_name: app1
    environment:
      - INSTANCE_NAME=app1
    networks:
      - highload-net
    # Порт наружу не открываем — доступ только через Nginx

  app2:
    build: .
    container_name: app2
    environment:
      - INSTANCE_NAME=app2
    networks:
      - highload-net

  app3:
    build: .
    container_name: app3
    environment:
      - INSTANCE_NAME=app3
    networks:
      - highload-net

  nginx:
    image: nginx:1.27-alpine
    container_name: nginx-lb
    ports:
      - "8080:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - app1
      - app2
      - app3
    networks:
      - highload-net

networks:
  highload-net:
    driver: bridge
```

**Разбор docker-compose.yml:**

- **`build: .`** — Docker Compose соберёт образ из Dockerfile в текущей директории. Все три сервиса `app1`, `app2`, `app3` используют один и тот же образ, но запускаются как отдельные контейнеры.
- **`networks: highload-net`** — все контейнеры находятся в одной виртуальной сети. Внутри этой сети они видят друг друга по именам сервисов (`app1`, `app2`, `app3`, `nginx`).
- **`ports: "8080:80"`** — Nginx слушает порт 80 внутри контейнера, но пробрасывает его на порт 8080 хоста. Мы используем 8080, чтобы не конфликтовать с системными сервисами на порту 80.
- **`volumes: ./nginx.conf:/etc/nginx/nginx.conf:ro`** — монтируем наш конфиг в контейнер Nginx. `:ro` означает read-only — контейнер не может изменить файл.
- **`depends_on`** — Nginx запустится после того, как запустятся `app1`, `app2`, `app3`. Это не гарантирует, что FastAPI уже готов принимать запросы, но гарантирует, что контейнеры созданы.

**Важно:** FastAPI-сервисы не открывают порты наружу. Они доступны только внутри Docker-сети. Это правильная архитектура безопасности: клиенты не могут обратиться к backend-сервисам напрямую, только через Nginx.

### Шаг 5. Запуск и проверка (10 минут)

**5.1. Соберите и запустите:**

```bash

```

Флаг `-d` запускает контейнеры в фоне (detached mode).

**5.2. Проверьте, что все контейнеры запущены:**

```bash
docker compose ps
```

Вы должны увидеть 4 контейнера: `app1`, `app2`, `app3`, `nginx-lb` — все в статусе `running`.

**5.3. Проверьте работу через Nginx:**


Запустите команду несколько раз. Вы должны увидеть, что ответы приходят от разных экземпляров:

Это означает, что балансировка работает. Nginx распределяет запросы между тремя экземплярами.

**5.4. Посмотрите логи Nginx:**

Вы увидите строки с `$upstream_addr` — адресами backend-серверов, которые обработали запросы:

### Шаг 6. Проверка отказоустойчивости (10 минут)

**6.1. Остановите один из экземпляров:**

```bash
docker compose stop app2
```

**6.2. Продолжайте отправлять запросы:**

```bash
for i in $(seq 1 10); do curl -s http://localhost:8080/ | grep -o '"instance":"[^"]*"'; done
```

Вы увидите, что все запросы обрабатываются `app1` и `app3`. `app2` исчез из ротации. Nginx обнаружил, что `app2` не отвечает, и исключил его из балансировки.

**6.3. Верните `app2`:**

```bash
docker compose start app2
```

Подождите 30 секунд (время `fail_timeout`) и снова отправьте запросы. `app2` вернётся в ротацию.

**Объяснение:** Это и есть пассивный health check. Nginx не опрашивает серверы активно — он обнаруживает проблему только тогда, когда запрос к упавшему серверу завершается ошибкой. После `max_fails=3` неудач сервер помечается как недоступный на `fail_timeout=30s`.

| `host not found in upstream` | Опечатка в имени сервиса | Имена в upstream должны точно совпадать с именами сервисов в docker-compose |
| Балансировка не работает | Все запросы идут на один сервер | Проверьте, что в upstream указаны все три сервера |
| Nginx не перезапускается | Ошибка в конфигурации | Выполните `docker compose logs nginx` для просмотра ошибок |

## Связь с последующими модулями

- **Модуль 3 (Базы данных):** Добавим PostgreSQL, и Nginx будет балансировать запросы, которые уже читают данные из БД.
- **Модуль 4 (Кеширование):** Добавим Redis, и Nginx сможет кешировать ответы.
- **Модуль 8 (Kubernetes):** В minikube Nginx Ingress Controller заменит standalone Nginx, а Deployment с репликами заменит три отдельных сервиса в docker-compose.
